# Understanding and capturing context — PL-04

PrincipalLoop keeps the premises and the files a proposal relies on. It can then show which of them changed. PL-04 delivers this mechanism, its checks and a local visual explorer. It launches no director and does not monitor Codex.

## Try it in one command

After [installation](DEVELOPMENT.md), from the repository root:

```powershell
principalloop demo            # or: uv run principalloop demo
principalloop demo --lang fr  # French report
```

Eight situations are actually run on disposable databases. The browser opens a self-contained HTML report: situation picker, explanation of the result, before/after comparison, dependencies, filter, file contents and technical references. No server, CDN, account or API key is needed. The report stays readable offline; it is frozen and performs no active monitoring.

To see the result right away without Python, open the [online demo](https://venorium.github.io/PrincipalLoop/), regenerated by the kernel on every publication, or the prebuilt [demo/index.html](demo/index.html) after downloading the repository. It contains synthetic data only. To check the kernel's behavior, replay the command above.

```powershell
# Generate without opening the browser; the path must be new.
.venv/Scripts/python -m principalloop demo --no-open --output "$env:TEMP/PrincipalLoop-demo.html"
# Optional machine summary, on another new path.
.venv/Scripts/python -m principalloop demo --no-open --json
```

| Situation | Expected result | What it tests |
|---|---|---|
| Everything is consistent | Reviewable | Versions and contents unchanged |
| Event without impact | Reviewable | The global sequence alone does not make a proposal stale |
| Assumption replaced | Needs review | Different business revision |
| Code changed | Needs review | Different digest despite an identical name |
| Unstable capture | Refused | Change detected between two reads |
| Undeclared read | Needs review | A served read stays checked even if the proposal omits it |
| Mandatory dependency | Needs review | The human scope cannot be omitted |
| Never-observed dependency | Limit shown | The check stays favorable despite the known gap: it does not prove completeness |

The expectations are fixed in the demo program and verified by the tests. The `demo-key-presence-v1` check only looks for a string in the captured bytes: it illustrates how they are bound to evidence, **not business idempotency**. The business oracle and the reserved variants belong to PL-08/13.

## Capturing your own work

The mission must already be initialized with `store init`: follow the [storage guide](STORAGE.md). All the following commands use the same workspace and the same state directory. The examples assume the current workspace and the default private state.

```powershell
.venv/Scripts/python -m principalloop context put --id H-1 --title "One order per request" --text "A retry keeps the same order." --event-id premise-1
.venv/Scripts/python -m principalloop snapshot capture --object H-1 --file README.md --event-id capture-1
.venv/Scripts/python -m principalloop snapshot list
.venv/Scripts/python -m principalloop snapshot inspect
```

`capture` keeps the bytes, then opens their report. `inspect` opens the latest capture; you can give its ID. Repeat `--file` or `--object` to select several items. `--no-open` skips opening and `--json` requests machine output. `--workspace` and `--state-dir` are the storage options. The CLI represents a trusted local operator; it is not an authorized interface for a model.

To revise a premise, reuse its ID with `--expected-revision 1`, the new text and a **new** `--event-id`. `--depends-on H-2` creates a dependency on an object that already exists. `context required --object H-1 --expected-revision 1 --event-id required-1` imposes a dependency; the current version can be read through the internal API `snapshots.policy()` (no dedicated command yet). A retry after a lost response reuses exactly the same arguments and the same ID; it returns the original capture even if the file has disappeared. A new capture uses a new ID.

Real reports stay outside the workspace and outside known synchronized directories, by default in the private `reports/` directory. An existing path is never overwritten. A real report contains the premises and a preview of the files: sharing it can disclose their content. Path exclusions are not a universal secret detector. Select only files you want to keep.

## What the kernel checks

An object has an identity, a kind, a content, a revision, relations and an author. Changing the content, sources or relations creates an immutable revision. Changing only the descriptive title keeps the revision. `depends_on`/`derived_from` cycles are refused. Replacing a premise marks its dependents "needs review" without declaring them false. A semantic revision of the dependent counts as its re-evaluation; a mere title rewording does not clear it.

The capture contains the journal cut, the mission/policy/plan versions, the selected objects and their dependencies, the file bytes and their SHA-256. The contents are stored as immutable BLOBs in the same private database. The manifest keeps the v0.1 contract. The identifier derives from the content and its cut; it is therefore not expected to stay identical after new events. The double read checks bytes and metadata. An unstable capture stays available for audit, but it cannot serve as evidence for an activation.

The future transport will open a session with `start_review`, serve each object/file through `read_context`, then record the proposal with `register_proposal(..., review_id=...)`. A read is journaled before it returns; the session closes on submission. `artifact` is a trusted inspection API, never a bypass to expose to the director.

Revalidation takes the union of the `read_set`, the served reads, the human dependencies and the link closure. **Every selected file is checked**, even if it is not declared in the `read_set`: a conservative convention, to be measured for false invalidations. Object revisions and file identity/version/path are compared. An ID declared twice is refused even if its revisions differ.

`Store.apply` checks freshness itself on publication, approval, acceptance and activation. A favorable `Checks` boolean cannot replace this check. A `STALE_CONTEXT` refusal keeps the state; the kernel can then record `MARK_STALE` when the machine allows it. An activation already started with effects to reconcile stays blocked: coordinating its resolution belongs to PL-05/06.

The verifier receives **the captured bytes** outside any SQL transaction. Its result keeps the digest computed on these bytes and the versioned ID of the check. Evidence can be reused for the same artifact and the same bytes; this proves neither the quality of the check nor its strategic relevance. The criteria remain the responsibility of the trusted verifier.

## Limits and presentation choices

- No atomic freeze of the workspace: a change followed by a return to the same bytes can escape the reads; a change after revalidation remains possible. No ENFORCED mode follows from this.
- Explicit capture: 64 files, 1 MiB per file, 8 MiB in total, 256 objects. No recursive walk. Canonical relative paths; symbolic links, reparse points and hard links refused. Some common sensitive directories and files are excluded.
- No isolation against a hostile program under the same Windows account, no delivered transport authentication, no guarantee of context completeness.
- The HTML is a read-only projection. The data in it is text, the scripts are local and controlled by a CSP; no file content is executed. Editing the HTML does not command the kernel.
- Words and causes carry the verdict; color is complementary. Keyboard navigation, visible focus, narrow layout, system colors and reduced motion are taken into account. Technical details expand on demand. No full WCAG audit is claimed.

The inversion test is embodied by the event without impact: a more recent journal is not enough to invalidate. The proof by contradiction is the omission case: reading "reviewable" as "complete truth" would give a false conclusion despite a correct check. The invariant concerns observable dependencies; the choice of colors and the conservative check of every file are explicit conventions.

## Migration and rollback

Storage moves to **format 2**, without changing the JSON Schemas or the identity of old events. Before migrating an existing v1 database, `Store` creates a consistent SQLite backup `before-storage-v2-<id>.sqlite3` next to the database. A migration interrupted before its commit leaves v1 intact; the next opening resumes the migration. `Reader` never migrates.

There is no downward migration. To go back to the PL-03 code, stop every owner, keep the v2 database and its WAL/SHM files separately, then use the v1 backup with the PL-03 code. The new PL-04 data is not present in that backup. Never replace the database of a live owner. General procedure: [STORAGE.md](STORAGE.md).
